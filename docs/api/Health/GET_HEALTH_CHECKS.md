## 3. Worker tracking
Singleton registry expects Delivery,OtpEmail,EventLogRetention. Disabled configured workers do not block. Enabled NotStarted/Stopped/Stalled/Failed/Recovering block readiness503. Running within time budget and Waiting within cadence healthy. Activity enum NotStarted=0,Running=1,Waiting=2,Failed=3,Stopped=4,Disabled=5; only in memory, PascalCase DTO strings, no DB enum changes. Public readiness exposes aggregate workers status, not names/timestamps/error codes. Operator detail: worker name,enabled,status,lastActivityAt,lastSuccessAt,lastFailureAt,consecutiveFailures. No message contents or exception messages.
Reporter activity wraps loop iterations/dequeue/send/finally, successful iteration resets failures. Delivery active stale after max(leaseSeconds,attemptTimeoutSeconds+30)+grace; Waiting stale after poll+grace. Retention active after runTimeout+grace; Waiting after interval+grace. OTP active after OtpStallSeconds default120 (10..1800), Waiting no stale timeout because idle queue awaits indefinitely. Health WorkerGraceSeconds default30 (5..300). Stale strict >threshold, equality still healthy. A worker reporting failed then retrying remains Recovering until success. Waiting OTP means queue await, not independently verified queue connectivity; stop/fault still tracked. OTP unexpected loop exceptions wait1second with shutdown cancellation before retry.

## 4. Responses and limits
ReadinessResponse(status,service,checkedAt,database,workers). HealthDetailsResponse(status,service,checkedAt,database{status,errorCode},workers[]). IHealthService provides detailed evaluation; thin public mapping strips details. All JSON camelCase. Overall Healthy only if DB healthy and enabled workers healthy; disabled retention valid even if it never ran. Worker state per process since boot, not historical uptime or cluster aggregation. Provider authentication/delivery outcomes and queue backlog do not determine loop health. No RabbitMQ check, BrokerHealthChecks writes, health history dashboard or queue metrics added here. DB outages normally keep /health200 while readiness503; configure deployment liveness/readiness accordingly.
